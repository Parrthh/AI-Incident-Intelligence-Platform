Alerts in. A clear explanation out.

When a website or app breaks, its monitoring sends alerts: short machine messages, often dozens at once, sometimes at 3 a.m. This project collects them into incidents and has an AI explain each one in plain language, so the engineer on call understands what's wrong faster. It's open source and anyone can run it.

Where the incidents on this site come from

No real company's systems are monitored here. To show the project working on real alerts, an automated test does this a few times a week:

  1. Starts a sample online store. The OpenTelemetry Demo, an open-source shop built from about 15 small services (cart, checkout, payment, shipping), with fake shoppers clicking around.
  2. Breaks it on purpose. It switches on a fault that makes every payment fail. This is called chaos testing.
  3. Lets monitoring notice. The store's monitoring (Prometheus) spots the jump in errors within a few minutes and sends alerts here.
  4. Fixes it and checks the result. The fault is switched off, the alerts clear, and the test checks that each incident was opened, summarized and closed.

The test runs in GitHub Actions, so every run is public. You'll often see two incidents per run: payment, and checkout, which fails because it depends on payment. Grouping those into one incident is the next milestone.

Alert
An automatic message from monitoring when a number crosses a line, like "more than 20% of payment requests are failing".
Incident
One problem worth a person's attention. It opens when an alert fires and closes when the alert clears.
On call
The engineer whose job it is to respond, at any hour, when an incident opens.

What happens when something breaks

The whole path, from alert to summary on screen, usually takes about a second here.

  1. Alert fires

    A Prometheus rule trips and Alertmanager posts the alert here.

  2. Stored once

    Retries and duplicates leave exactly one record, even when ten copies arrive at the same moment.

  3. Grouped

    Alerts on related services (checkout calls payment) join one incident, and the timeline says why.

  4. Summary written

    A background worker strips out secrets, then an AI model (Gemini) writes two or three sentences from the alert data alone.

  5. Evidence gathered

    Once alerts settle, it gathers the alerts, recent deploys and, where connected, error logs, failing traces and metrics, each with a short ID.

How it's built

Python, FastAPI, Postgres with pgvector, Redis, and Gemini, deployed from GitHub on every merge. A few of the decisions behind it:

Tested by breaking things
A GitHub Actions job runs the OpenTelemetry Demo, makes its payment service fail, and checks that an incident and summary appear and then resolve.
Duplicate-proof ingestion
An atomic upsert keyed on the alert's fingerprint and start time, plus a guard that a late retry can't reopen a resolved alert.
No secrets reach the model
Passwords, tokens, API keys and email addresses are redacted from every prompt. Each summary records its model, prompt version and token counts.
Nothing lost on a restart
The alert and its "write a summary" job are saved together in one database transaction, then queued in Redis. Failed jobs retry with growing waits; a crashed worker's job is picked up by another.
Every deploy is verified
After a merge, a job waits until this site reports the new commit, then checks that the database and Redis are reachable.
